# TFA7: Making It Editable in Laravel

A classroom POS directory with customer and user creation, server validation, prefilled edit forms, and prepared avatars. The complete Laravel skeleton and dependency lock file are generated by the setup commands below; the lab-kit overlay supplies the coursework implementation.

## Requirements

- PHP 8.2–8.5 with the usual Laravel extensions plus GD, mbstring, fileinfo and PDO SQLite (or PDO MySQL on hosting).
- Composer 2.
- Laravel 12, selected for the computer lab's PHP 8.2. Laravel 13 needs PHP 8.3 or later.
- `intervention/image:3.*`. The handout requires an instructor-approved image package but does not name it. Confirm this package with your instructor if your class specified a different one.

## Install from this GitHub repository

Clone or download and extract the source. Open PowerShell in the project root (the folder containing `artisan`), then run:

```powershell
composer install
Copy-Item .env.example .env
New-Item -ItemType File -Path database\database.sqlite
php artisan key:generate
php artisan optimize:clear
php artisan migrate --seed
php artisan test
php artisan serve
```

These database-creation commands assume a fresh checkout without an existing local database or `.env`. Keep an existing database and configuration when resuming saved work. With portable Composer, replace `composer` with `php "$env:USERPROFILE\LaravelLabTools\composer.phar"` and set `PHPRC` as described in the lab guide.

Open `http://127.0.0.1:8000`. The kit uses plain CSS in `public/css/pos.css`, so these pages need no npm build. Local SQLite avoids needing a database service on the lab PC; hosting uses MySQL. If your instructor specifically requires local MySQL, set the matching `DB_*` values, create an empty database and run the same migrations/seeders there instead.

## Pages and validation

| Page | Behavior |
| --- | --- |
| `/` and `/about` | Home counts and project description |
| `/customers` | Lists customer records; create and edit links |
| `/customers/create` | Requires full name and valid email; phone is optional |
| `/customers/{customer}/edit` | Prefills and updates the chosen customer |
| `/users` | Lists usernames, full names and avatar/placeholder |
| `/users/create` | Requires unique username and full name |
| `/users/{user}/edit` | Prefills fields; optional JPEG/PNG/WebP avatar up to 2 MB |

Errors appear beside the corresponding field. Text values are retained after validation failure. Forms use CSRF tokens and edit forms spoof PUT. This is a coursework directory; login, access roles and deletion are outside the assignment implemented here. All sample records are fictional.

## Avatar handling

The dedicated migration adds a nullable `users.avatar` string column. Intervention Image v3 with GD decodes each valid upload, crops/resizes it to 256 × 256 pixels and re-encodes it as PNG. `Storage::disk('public')` writes `avatars/<UUID>.png` under `storage/app/public`. Only this path goes in the database. A constrained image route reads that directory and returns the prepared image; therefore neither Windows administrator symlinks nor `storage:link` is needed. Existing pictures are kept when editing without a new file, and old pictures are removed after a successful replacement. Users without pictures show the bundled SVG placeholder.

## Tests

```powershell
php artisan test
```

Feature tests cover list/form pages, required and invalid fields, duplicate usernames, update uniqueness, old input, image type and size, real 256-pixel PNG conversion, avatar delivery/replacement/preservation, placeholders and export escaping. Test databases use in-memory SQLite. The authoring environment had no PHP runtime, so the supplied tests must be run on the lab PC before treating the application as verified.

## Export current records for InfinityFree

After finishing local demonstrations:

```powershell
php artisan lab:export-mysql
```

Import the generated `database/exports/tfa7-current-data.sql` into a NEW EMPTY MySQL database through hosting phpMyAdmin. It contains current customers/users, including paths to your prepared avatars. Copy the corresponding avatar files with the hosting build. The export deliberately does not drop existing tables; it is for initial installation, not a schema upgrade. Once the hosted database exists, do not import it again. Migrations and seeders remain the portable source of the initial schema/data.

Use the kit's hosting guide and templates. Prepare production dependencies locally; upload `vendor` to hosting but exclude it from GitHub. Keep the standard `public/.htaccess` and add the supplied root `.htaccess` in `htdocs`. The host-only `.env` uses production mode, MySQL and file-based sessions/cache. Do not upload source/config/logs into `public`. Do not publish `.env`, database files or credentials to GitHub.

## Files to understand for the laboratory demonstration

- `routes/web.php`: routes and model binding.
- `app/Models`: Eloquent tables, fillable properties, timestamps settings.
- `app/Http/Controllers`: querying, validating, creating and updating.
- `app/Services/AvatarService.php`: image preparation and public-disk storage.
- `resources/views`: Blade lists/forms, CSRF, errors, old values and placeholders.
- `database/migrations` and `database/seeders`: schema and fictional starter records.
- `tests/Feature`: executable checks for the required behavior.
